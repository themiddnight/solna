# Internationalization (i18n) — Codebase Reference

> How murva's frontend does localization with **Lingui v6**. Read this before
> adding UI text, a new locale, or touching any i18n config. Related: the
> `no-literal-string` lint gate (TR-35) and the locale-persistence policy (TR-41)
> in [`RULES_AND_CONSTRAINTS.md`](../../../docs/RULES_AND_CONSTRAINTS.md).

## Overview

Localization is **frontend-only** (the backend sends locale-agnostic data/keys).
The stack is [Lingui](https://lingui.dev) v6 with the SWC macro transform, PO
catalogs, and ESLint enforcement that **fails the build on un-wrapped JSX text**.

- **Locales**: `en` (source) and `th`. English is the source locale — `msgid`s
  are the English text itself, so untranslated strings fall back to English.
- **Catalogs**: PO files under `src/locales/{locale}/messages.po` (source,
  human/AI-editable). `i18n:compile` emits `messages.js`; it is committed but
  currently unused at runtime — the app imports the `.po` through the Lingui
  Vite plugin (dev/test parity comes from the Vite/SWC plugins, not the `.js`).
- **Locale persistence**: stored in `localStorage` under `murva_locale`; there is
  no browser-language detection — an unset locale always starts as `en` until the
  user picks one (TR-41).

## Usage patterns

Import macros from the **`/macro` entry points** — they are compiled away at build time.

```tsx
// JSX text → <Trans>
import { Trans } from "@lingui/react/macro";
<h1><Trans>Account Settings</Trans></h1>

// Strings (attributes, toasts, console, non-JSX) → t``
import { t, plural } from "@lingui/core/macro";
title={t`Lock Project`}
toast.error(t`Failed to save "${{ name: project.name }}"`);
plural(count, { one: t`# project`, other: t`# projects` });

// Reactive strings inside a component (re-renders on locale change) → useLingui
import { useLingui } from "@lingui/react/macro";
const { t } = useLingui();
```

- **JSX visible text** → `<Trans>`. **Everything else** (attribute values, `title`,
  `data-tip`, toast/console messages, computed labels) → `` t`...` ``.
- Interpolate with **named placeholders**: `` t`Hello ${{ name: userName }}` `` —
  this keeps catalog keys stable and translatable.
- Use `plural()`/`select()` for count- and gender-dependent text; never concatenate.
- `useLingui()` (`@lingui/react/macro`) when a string must re-render on locale switch.

## Scripts & workflow

| Command (in `app/frontend/`) | Does |
|---|---|
| `bun run i18n:extract` | Scans `src/` for macros, writes new `msgid`s into every `messages.po` |
| `bun run i18n:compile` | Compiles `.po` → `.js` (runtime catalogs). Runs automatically at the start of `bun run build` |

**Adding/changing a user-facing string**
1. Wrap it (`<Trans>` or `` t`` ``).
2. `bun run i18n:extract` → the new English `msgid` lands in `en` and `th` `.po`.
3. Add the Thai `msgstr` in `src/locales/th/messages.po` (leave blank to fall back to English).
4. `bun run i18n:compile` (or just `bun run build`).

**Adding a new locale**
1. Add the code to `locales` in `lingui.config.ts` (drives extraction).
2. Add the code to `locales` in `src/shared/utils/i18n.ts` (the saved-locale validation
   allow-list — without this, `getSavedLocale()` rejects it and falls back to `en`).
3. Add the code + display label to `localeLabels` in
   `src/shared/components/LanguageSelect.tsx` (the map the switcher actually renders).
4. `bun run i18n:extract` to generate `src/locales/<code>/messages.po`, translate, `i18n:compile`.

## Translation conventions

When writing a non-English `msgstr` (e.g. Thai), **transliterate / keep the source
term** (ทับศัพท์) instead of inventing a native translation in these cases:

1. **Product terms** — murva's own feature/concept names. Keep them recognizable
   and consistent with the UI/marketing. Examples: **Arrange Room**, **Perform Room**,
   **Companion(s)**, **Stage**, **Mixdown**, **Stems**.
2. **Musical terms** — standard music vocabulary that musicians already know in
   English/loanword form. Examples: **BPM**, **velocity**,
   **arpeggiator**, **sustain**, **swing**, **quantize**, **MIDI**.
3. **Audio effect names — always transliterate (no exceptions).** Every effect
   name stays in its source form: **reverb**, **delay**, **compressor**, **EQ**,
   **flanger**, **chorus**, **distortion**, **phaser**, **gain**, etc.
4. **Effect & synth parameters — always transliterate.** Parameter labels and
   controls in both the effect chain and the synthesizer stay in source form:
   **attack**, **decay**, **sustain**, **release**, **cutoff**, **resonance**,
   **threshold**, **ratio**, **mix**, **feedback**, **rate**, **depth**,
   **wet/dry**, **Q**, etc.
5. **Clarity judgment** — any other term where, after consideration, the
   transliterated/English form reads **more clearly** for the target user than a
   forced literal translation. When in doubt, prefer the form a real user of that
   language would actually use.

Notes:
- Transliterate means keep the term as a loanword (in the target script where
  natural, e.g. Thai "คอร์ด" for *chord*), **not** translate to a coined equivalent.
- Be **consistent**: once a product/musical term has a chosen form, reuse it across
  every catalog entry.
- This is editorial guidance for catalog (`.po`) translations — it does **not**
  change how strings are wrapped in code (still always via macros, see TR-35).

## Invariants & gotchas

1. **No literal user-facing strings** — `i18next/no-literal-string` runs in
   `jsx-only` mode and is an **error**, so bare JSX text fails `bun run lint:fe`
   and CI. Codified. Non-translatable attrs are allow-listed in `eslint.config.js`
   (`className`, `id`, `data-*`, `aria-*`, Konva/SVG presentation attrs, `storageKey`, …);
   `<Trans>`, `Link`, `Icon` are excluded as components. Extend those lists rather
   than disabling the rule inline. See TR-35.
2. **`t` macro must be called inside a function/component** — `lingui/t-call-in-function`
   is an error. Don't lift `` t`...` `` to module top level; use `msg`` ` `` (lazy)
   from `@lingui/core/macro` for module-scope definitions and translate at use site.
3. **Import from `/macro`** — `@lingui/react/macro` and `@lingui/core/macro`, not the
   runtime `@lingui/react` / `@lingui/core`. The SWC plugin only transforms the macro entries.
4. **`messages.js` is committed but unused at runtime** — after
   `i18n:extract`/translation, `i18n:compile` regenerates `messages.js` and it is
   still committed, but nothing imports it: the app loads the `.po` directly
   through the Lingui Vite plugin (dev/test parity comes from the Vite/SWC
   plugins, not the `.js`).
5. **PO line numbers are off** (`lineNumbers: false`) so catalogs don't churn on
   unrelated edits — diffs stay to real string changes.
6. **Tests** activate an empty `en` catalog (`src/test/setup.ts`), so assertions can
   match the English source text directly. `vitest.config.ts` must keep
   `linguiMacroSwcPlugin()` or macros won't transform and tests will see raw macro calls.
