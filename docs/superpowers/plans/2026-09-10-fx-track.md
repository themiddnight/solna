# FX Melody Track Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a sixth track, `fx`, that is a twin of the lead melody track — its own per-loop
note grid, synth patch, bus, fader, mute, solo, transport player, Pattern segment and Sound-view
control target — playing alongside the lead rather than instead of it.

**Architecture:** Every FX field is a NEW key added beside its lead sibling (never a reshape of
an existing one), because this repo has no migration chains: a missing key takes its default on
read, while a key whose shape changed fails validation and is REPLACED by the default, blanking
stored content. Code symmetry comes from one new table, `MELODY_TRACKS` (`src/store/melodyTracks.ts`),
which spells out both tracks' store field names as table data on the `SOURCE_BUSES` precedent;
`leadSlice`, the `lead/` hooks and `LeadMelodyGrid` read their fields through that table under a
required `trackId`. `src/audio/leadMelody.ts` and `src/components/loop/lead/melodyGrid.ts` are
already track-agnostic (they take notes, `stepsPerBar` and `stride` as arguments and read no store
field), so they change only where a signature has to widen — see Task 2.

**Tech Stack:** TypeScript, React 19, Zustand (`subscribeWithSelector` + `persist`), raw Web Audio
API, Tailwind v4 + daisyUI v5 (CSS-first themes, no `tailwind.config.*`), Bun test runner
(`bun:test`, `renderToString` from `react-dom/server`, no DOM and no testing-library), Lucide icons.

**Spec:** docs/superpowers/specs/2026-09-10-fx-track-design.md

## Global Constraints

- **Four import layers, enforced by eslint.** `src/data/` imports nothing at runtime (not even a
  sibling in `src/data/`), reads no impure global, declares no function and constructs nothing with
  `new`; `src/audio/` never imports `store/` or `components/`; `src/store/` never imports
  `components/`; `src/components/` must not import `audio/engine`. `src/utils/` sits outside the
  chain, above `data/`.
- **`bun run verify` is the completion gate.** It runs `bun test && bun run lint && bun run eslint
  && bun run check:keys && bun run check:drums && bun run check:contrast && bun run check:levels &&
  bun run build`. Run it before claiming any task complete that says so.
- **`bun run eslint` must report NOTHING — no errors and no warnings.** That is the repo's current
  state and the state to keep it in. A new `react-hooks/exhaustive-deps` or `complexity` warning is
  a failure of this plan; fix the code, or add a line disable naming its reason.
- **No meter value may enter a zustand slice.** A write per tick re-renders every mounted view.
- **Never call an engine setter from a component.** Add the state to a slice and wire it in
  `src/store/engineSync.ts`.
- **No migration chains.** `PERSIST_VERSION` and `PROJECT_FORMAT_VERSION` are stamped on every
  write and drive no read-time transform. A persisted shape change is handled by validating the new
  key in `sanitizePersistedState`/`sanitizeLoops` (store.ts / sanitize.ts) and `sanitizeContent`
  (projectFile.ts) — never by bumping a version and never by adding a version-gated branch.
  **Neither version moves in this plan.**
- **Adding a key is safe; reshaping one is not.** A missing key takes its default on every read
  (correct for a project written before FX existed). A key whose shape changed fails validation and
  is REPLACED by the default — the stored content is gone. Every FX field below is therefore
  additive.
- **Every Tailwind class string stays a literal.** Tailwind v4 scans source statically, so a class
  assembled from `--color-module-${target}` at runtime is never emitted.
- **Components name roles, never colours.** No raw hex, no Tailwind palette classes
  (`indigo-*`, `slate-*`, `teal-*`, …), no `text-white`/`bg-black`, no `dark:` variant, no
  `rgb()`/`rgba()` literal in `src/**/*.{ts,tsx}`. `scripts/themeTokenGuard.ts`'s `ALLOWLIST` is
  empty and must stay empty — fix the code, not the allowlist. Hex literals belong in
  `src/index.css` only.
- **No `React.FC`** (eslint error). `consistent-type-definitions` is an error — declare object
  types with `interface`, not `type X = { … }`.
- **No `../../` imports.** Two or more `../` levels are banned globally; use the `@/` alias. A
  single `../` is fine.
- **`bun:test` does not export `it`** in this repo. Import `test`, `describe`, `expect`, `spyOn`,
  `beforeEach`, `afterEach` from `'bun:test'`. There is no DOM and no testing-library, and none may
  be added.
- **Commit messages, code, comments and docs are in English.**
- Branch is `feat/fx-track`, already checked out. Each task ends with its own commit.

## Vocabulary this plan uses

| name | where | value |
| --- | --- | --- |
| track id | `MELODY_TRACKS[].id` | `'lead'` \| `'fx'` |
| engine source | `SOURCE_BUSES[].source` | lead → `'synth'`, fx → `'fx'` |
| solo track | `SOLO_TRACKS` | lead → `'lead'`, fx → `'fx'` |
| control target | `SynthControlTarget` | lead → `'synth'`, fx → `'fx'` |
| mix layer id | `MIX_LAYER_IDS` | lead → `'synth'`, fx → `'fx'` |
| step player id | `StepPlayerId` | lead → `'lead'`, fx → `'fx'` |
| player module | `PlayerModule` | lead → `'lead'`, fx → `'fx'` |

The lead row is irregular in four of those columns and the fx row in none. That asymmetry is the
whole reason `MELODY_TRACKS` spells its field names out instead of deriving them from `` `${id}…` ``.

## Scope decisions this plan makes that the spec left open

- **FX gets session-only `fxCursor` and `fxBarClipboard`,** mirroring `leadCursor` /
  `leadBarClipboard`. Those two lead fields are NOT in `LOOP_FLAT_KEYS` (they are session state), so
  the fx twins are additive with zero persist impact — and without them the two grids would share
  one cursor and one clipboard, so moving the FX cursor would move the lead's playhead selection.
- **FX has no live recorder.** `leadRecording`, `store/leadRecord.ts`'s `leadMarkerFollowsClock`
  and the note-input dispatcher path are lead-only and stay that way; the FX grid renders no Rec
  button, and its step publisher's gate is simply `fxPlayer !== 'stopped'`. Widening live capture to
  a second track is a separate design.

## Task 1: The FX module colour

Deliberately first. A colour picked to look right beside the existing four and checked at the end
is a colour that gets re-picked after the UI is built against it.

**Read `.claude/rules/theming.md` before starting** — it auto-loads for `src/index.css` and
`scripts/themeTokenGuard.ts` and states the hard rule this task works under.

**Two facts you need that the spec gets wrong, verified against the source:**

1. **`bun run check:contrast` does NOT cover module colours.** `scripts/check-drum-contrast.ts`
   brace-matches the block containing `--drum-kick` and iterates `DRUM_TYPES` only. The "closest
   pair clears 4.5 by a few thousandths" line in CLAUDE.md is about the DRUM palette, not the module
   palette. Adding a module colour therefore trips no existing gate at all.
2. **The light module palette is already below AA in three places** — `osc` 4.409, `chord` 4.471,
   `env-vca` 4.201 against their own `-content`. Do NOT add a gate that asserts AA over the whole
   module palette: it would fail on three colours this task did not touch, and retuning them is a
   different piece of work. Assert the floor for the **`fx` pair only**.

**The hue, and the derogation it forces.** `src/index.css` states "Every adjacent pair is at least
28° apart" over `osc 87 · chord 125 · env-vca 162 · lfo 213 · bass 256 · env-vcf 294 · arp 322 ·
filter 356`, with `pad` at 40° as the one recorded exception inside the reserved 20-60° amber band.
The largest gap in that ring is 162→213 (51°), so a ninth hue can be at most 25.5° from its
neighbours: **28° is not achievable and the comment must be corrected, not silently violated.**
FX takes **187°**, 25° from env-vca and 26° from lfo.

describe('module palette — the fx pair clears AA in both themes', () => {
  // Scoped to `fx` on purpose, NOT the whole module palette: three of the
  // existing LIGHT module colours (osc 4.409, chord 4.471, env-vca 4.201) sit
  // below 4.5:1 today, and retuning them is not this change's job. What this
  // pins is that the colour ADDED here is not a fourth one.
  //
  // The maths is a local copy of scripts/check-drum-contrast.ts's, deliberately:
  // that file is a standalone bun script with no exports, and giving it exports
  // so a test could import them would make a CLI gate carry a library API.
  const css = readFileSync(join(import.meta.dir, '..', 'src', 'index.css'), 'utf8');

  function lin(channel: number): number {
    const c = channel / 255;
    return c <= 0.04045 ? c / 12.92 : ((c + 0.055) / 1.055) ** 2.4;
  }
  function relativeLuminance(hex: string): number {
    return (
      0.2126 * lin(parseInt(hex.slice(1, 3), 16)) +
      0.7152 * lin(parseInt(hex.slice(3, 5), 16)) +
      0.0722 * lin(parseInt(hex.slice(5, 7), 16))
    );
  }
  function contrastRatio(a: string, b: string): number {
    const [hi, lo] = [relativeLuminance(a), relativeLuminance(b)].sort((x, y) => y - x);
    return (hi + 0.05) / (lo + 0.05);
  }

  // Both --module-fx declarations, in file order: the dark block (`:root,
  // [data-theme="solna-dark"]`) precedes the light one in index.css. Asserting
  // the COUNT is what keeps that assumption honest — a third declaration, or a
  // block reordering, fails here rather than measuring one theme twice.
  const fills = [...css.matchAll(/--module-fx:\s*(#[0-9A-Fa-f]{6})/g)].map((m) => m[1]);
  const contents = [...css.matchAll(/--module-fx-content:\s*(#[0-9A-Fa-f]{6})/g)].map((m) => m[1]);

  test('declares exactly one fx pair per theme', () => {
    expect(fills).toHaveLength(2);
    expect(contents).toHaveLength(2);
  });

  test('dark fx clears the 4.5:1 AA floor', () => {
    expect(contrastRatio(fills[0], contents[0])).toBeGreaterThanOrEqual(4.5);
  });

  test('light fx clears the 4.5:1 AA floor', () => {
    expect(contrastRatio(fills[1], contents[1])).toBeGreaterThanOrEqual(4.5);
  });

  test('fx carries a 10% tint derived from its own fill, per theme', () => {
    const tints = [...css.matchAll(/--module-fx-tint:\s*(#[0-9A-Fa-f]{8})/g)].map((m) => m[1]);
    expect(tints).toEqual([`${fills[0]}1A`, `${fills[1]}1A`]);
  });
});

## Task 2: The `MELODY_TRACKS` table

A PURE REFACTOR. No new store field, no behaviour change, the whole existing suite stays green.

**A spec correction you need before you start.** The spec says "the `audio/leadMelody.ts` helpers
… take a track id instead of hardcoding lead, and read their fields through the table." They do
not read any store field: every exported helper (`leadStoredIndexAt`, `leadActivePosAt`,
`leadSoundingNotes`, `resizeLeadMelody`, `resolveLeadStepTriggers`, `clampLeadCursor`,
`copyLeadBar`, `pasteLeadBar`, …) already takes the note matrix, `stepsPerBar` and `stride` as
arguments — `src/audio/` may not import `src/store/` at all, which is what forced them to be pure
in the first place. The same is true of `src/components/loop/lead/melodyGrid.ts`. **Adding a track
parameter to them would be an unused parameter**, which `bun run eslint` reports and the gate
forbids. Leave both files alone. The parameterisation this change actually needs is in `leadSlice`
(Task 6) and the hooks/component (Task 7), which read `s.leadMelodySteps` and its siblings off the
store — and that is exactly what the table below exists to name.

**Files:**
- Create: `src/store/melodyTracks.ts`, `src/store/melodyTracks.test.ts`

- Consumes: nothing. The module imports no value — only `import type` — so it is as cheap to reach
  from `src/components/` as `store/sourceBuses.ts` is, and for the same reason.

  - `const MELODY_TRACKS` — the two rows, `as const`

 * The two melody tracks — Lead and FX — as `[store field names, player, engine
 * source, vocabulary]`. `leadSlice`, the `lead/` hooks and `LeadMelodyGrid` read
 * their fields through this table under a required `trackId`, so the two tracks

 * store, and `melodyTrack()` is a function — src/data/ declares none. It sits
 * beside sourceBuses.ts instead, which is the same shape (a store table with no

    controlTarget: 'synth',

    id: 'fx',
    label: 'FX',
    steps: 'fxMelodySteps',
    loopLength: 'fxLoopLength',
    stepResolution: 'fxStepResolution',
    view: 'fxMelodyView',
    octave: 'fxMelodyOctave',
    gate: 'fxGate',
    synthParams: 'fxSynthParams',
    volume: 'fxVolume',
    muted: 'fxMuted',
    cursor: 'fxCursor',

    module: 'fx',
    stepPlayer: 'fx',
    engineSource: 'fx',
    solo: 'fx',
    controlTarget: 'fx',

export type MelodyTrack = (typeof MELODY_TRACKS)[number];

/** `'lead' | 'fx'` — the required `trackId` prop's type. */
export type MelodyTrackId = MelodyTrack['id'];

/**
 * Compile-time cross-checks against the two vocabularies this table translates
 * into. A typo in `solo` or `controlTarget` is then a build error rather than a
 * track that silently never solos, or a Sound view that falls back to the lead
 * channel. Nothing here survives compilation.
 */
// eslint-disable-next-line @typescript-eslint/no-unused-vars
type AssertSoloTracks = MelodyTrack['solo'] extends SoloTrack ? true : never;
// eslint-disable-next-line @typescript-eslint/no-unused-vars
type AssertControlTargets = MelodyTrack['controlTarget'] extends SynthControlTarget ? true : never;

/** Narrow a track id to its row. Undefined is impossible for a `MelodyTrackId`. */
export function melodyTrack(id: MelodyTrackId): MelodyTrack {
  return MELODY_TRACKS.find((track) => track.id === id) as MelodyTrack;
}

**Why this is a task and not a detail.** `engineSync.ts` watches a bitmask over the players and
calls `audioEngine.resetClock()` only on the fully-stopped → active transition, whose whole
correctness argument is *"'fully stopped' means ALL players are 'stopped'"*. An `fxPlayer` missing

under it.

**And why the publisher id is a closed union.** `components/playbackStep.ts` types its key as
`StepPlayerId = 'chords' | 'lead' | 'sequencer'`, backed by a `PLAYER_IDS` array. It is not a free
string, so the FX grid cannot simply pass a new key. Miss this and the two grids write the same
publisher slot — the FX playhead drives the lead's marker and vice versa, at whichever grid's
stride published last, with no error anywhere.

```ts
export function useLeadStepPublisher(trackId: MelodyTrackId): void {
  const track = melodyTrack(trackId);
  // Lead follows the WIDER gate — its marker must also track somebody else's
  // clock while Rec is armed, because that column is where live capture writes
  // (store/leadRecord.ts says why that is not simply the recorder's own gate).
  // FX has no recorder, so its marker follows its own player and nothing else.
  const followsClock = useAppStore((s) =>
    trackId === 'lead' ? leadMarkerFollowsClock(s) : s.fxPlayer !== 'stopped',
  );

  useEffect(() => {
    if (!followsClock) {
      resetStep(track.stepPlayer);
      return;
    }

    initPlaybackEngine();

    return subscribePlaybackClock((step, _beat, time) => {
      const s = useAppStore.getState();
      const stepsPerBar = getMeter(s.meterId).stepsPerBar;
      const stride = strideFor(s[track.stepResolution]);
      const columns = s[track.loopLength] * columnsPerBar(stepsPerBar, stride);
      const tickDur = stepDurationSec(s.bpm) / TICKS_PER_SIXTEENTH;
      for (const hit of leadMarkerPublishes(step, stride, columns, tickDur)) {
        publishStepAt(track.stepPlayer, hit.column, time + hit.offsetSec);
      }
    });
  }, [followsClock, track]);
}
```

`track` is a stable module-scope object (`melodyTrack` returns a row of a frozen-by-`as const`
literal), so listing it in the dependency array satisfies `react-hooks/exhaustive-deps` without
re-subscribing. Do not omit it — a `// eslint-disable` here would be hiding the one dependency that
decides which slot is written.
