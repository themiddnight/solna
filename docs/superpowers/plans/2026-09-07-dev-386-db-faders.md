# DEV-386: Every user-facing level in dB — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Store, migrate and display every user-facing level — `masterVolume`, the five bus faders, and `SequencerTrack.volume` — in decibels on a DAW-style taper, converting to linear gain only at the store→engine boundary, and separate a **fader level** from a **performance velocity** everywhere the two are currently conflated.

**Architecture:** The seven keys change unit in the store; every existing engine setter keeps its linear signature, because `src/store/engineSync.ts` wraps each call site in `faderDbToGain()`. **One component owns the taper:** `src/components/ui/VolumeFader.tsx` converts position ↔ dB, formats through `formatDb`, holds unity at 0.75 of travel, returns to 0 dB on double-click and detents to true silence at the bottom of travel — and roughly twenty call sites consume it (the transport master, five `ChannelStrip` users, five loop-card bus faders, eleven per-track drum faders). Three audio-path corrections ride along, because a dB fader over a wrong law is a wrong law you can now read precisely: the sequencer fader stops being applied twice (once as a bus gain and once as a drum velocity, making drum output proportional to its square), `SequencerTrack.volume` becomes a real per-track `GainNode` in front of the drum bus rather than a velocity multiplier, and the two engine clamps that cap gain at `1.5` and `1.0` — which make the top 8.5 dB of every bus fader and *all* of the master fader's boost do nothing — are raised to `MAX_FADER_GAIN`, derived from the fader range itself. Each unit change lands with its own migration step in both chains — persist `16 → 17 → 18 → 19`, project `formatVersion 7 → 8 → 9 → 10` — so no guard ever ships ahead of its final output.

**Tech Stack:** TypeScript, React 19, zustand (`persist` + `subscribeWithSelector`), Bun test runner, daisyUI 5 / Tailwind v4 (CSS-first themes).

**Spec:** Linear DEV-386; shared contract at `docs/superpowers/plans/2026-09-07-dev-383-gain-staging-contract.md`

## Global Constraints

- `UNITY_DB = 0`, `UNITY_GAIN = 1` — unity is 0 dB and linear 1.
- `SILENCE_DB = -60` — the **stored** representation of silence (divergence #2: `JSON.stringify(-Infinity)` is `null`, and these keys cross `JSON.stringify` twice).
- `DISPLAY_FLOOR_DBFS = -60` — the fader bottom and the silence value are the same place.
- `FADER_MAX_DB = +12`; the fader range is `-60 .. +12` dB.
- `DEFAULT_UNITY_POS = 0.75` — 0 dB sits at three-quarters of physical travel.
- `dbToGain(-60) = 0.001`, `dbToGain(-6) ≈ 0.501`, `dbToGain(0) = 1`, `dbToGain(12) ≈ 3.981`.
- `MAX_FADER_GAIN = dbToGain(FADER_MAX_DB) ≈ 3.981` — the linear ceiling, **derived** from the fader range, never restated as a literal. It is what both engine clamps clamp to.
- **`faderDbToGain(SILENCE_DB)` is exactly `0`, not `dbToGain(-60)`'s `0.001`.** The bottom of a fader is silence in every DAW, and `faderDbToGain` — not `dbToGain` — is what the store→engine boundary calls. `dbToGain` itself is untouched and still returns `0.001` at −60; the two are different questions.
- `formatDb` is the **only** display formatter for a dB value. Do not write a second. It renders `SILENCE_DB` as `-∞ dB`.
- **`VolumeFader` is the only component that converts between slider position and dB.** No call site may call `dbToSliderPos`/`sliderPosTodB` itself; that is what makes "unity at 0.75 of travel" true by construction across ~20 faders instead of true by repetition.
- `src/audio/` keeps receiving linear gain. **No EXISTING engine setter signature changes.** One new setter is added — `setDrumTrackGain(instrument: string, gain: number): void` — and it takes linear gain like every other. Two existing setter *bodies* change: `setSourceGain` and `setMasterVolume` raise their clamp ceiling to `MAX_FADER_GAIN`. A ceiling is not a signature.
- **A fader value is never passed into a velocity parameter, and a velocity is never written to a gain node a fader owns.** A velocity is a per-hit performance attribute in 0..1 (MIDI `data[2] / 127`, a pad's strike strength, a step accent); a gain is a level a fader owns and may exceed 1. `clampVelocity` in `src/audio/constants.ts` clamps to 0..1, so a fader routed through it cannot even express the +12 dB the range promises.
- Engine setters are called only from `src/store/engineSync.ts` (layering rule 3); the one pre-existing exception this plan touches is `useSequencerPlayback.ts`, which reaches audio through the `audio/playback/` bridge, not through a setter.
- Internal voicing constants stay **linear** and are out of scope: drum-kit `gain`/`clickLevel`/`bodyGain`/`noiseGain`/`reverbSend`, preset `subOscVolume`/`noiseVolume`, vibe pad `volume`, `DEFAULT_PADS` `volume`. DEV-387 owns their consistency.
- Persist `version` and project `formatVersion` are **separate chains and are never merged**; `mapLoops` (persist) and `mapBodyLoops` (body) stay two copies. Persist runs `16 → 17 → 18 → 19` (16 is DEV-385's, see the precondition); project runs `7 → 8 → 9 → 10`. The two chains are at different numbers on purpose and must not be aligned.
- `bun run verify` is the gate and `bun run eslint` must report **nothing at all** — no errors, no warnings.
- No DOM and no testing-library. Tests are `bun:test`; markup tests use `renderToString`. `useAppStore.setState()` before a `renderToString` has no effect (zustand serves creation-time state) — see `.claude/rules/testing.md`.
- Components name theme **roles**, never colours; `bun run check:theme` must pass.
- Branch: `feat/dev-386-db-faders`. Conventional commits.

## Design decisions taken in this plan

**1. `ChannelStrip`'s `max` prop is deleted, not converted to a dB ceiling.**
Today `max` is a linear ceiling — `1.5` for a boostable layer, `1.0` for the drum bus — and it is required precisely because the ceiling was a property of the bus. Under a single `-60..+12` dB range that distinction is gone: every bus can be pushed 12 dB and pulled to silence. Keeping `max` as a *dB* ceiling would be actively harmful, because `dbToSliderPos` derives the taper from `FADER_MAX_DB`; a per-call ceiling would make the same physical position mean a different dB on different strips, which is exactly the inconsistency the epic exists to remove. `LOOP_MIX_CHANNELS` in `SortableLoopCard.tsx` loses its `max` field for the same reason.

**2. Fader `step` is a position step, not a dB step.**
The `<input type="range">` runs `min=0 max=1 step=FADER_POSITION_STEP` where `FADER_POSITION_STEP = 0.005` (200 detents). A fixed dB step is wrong on a tapered control: it would be coarse at the bottom and absurdly fine at the top, or the reverse. At 0.005 of travel a detent is ~0.4 dB below unity and ~0.24 dB above it — fine enough to be smooth under a pointer, coarse enough that a keyboard arrow does something visible. The *displayed* dB is rounded by `formatDb` (one decimal), never by the control. `VolumeFader` (decision 10) is the only place this is written down.

**3. Factory defaults become exactly 0 dB, for all seven keys.**
The old linear defaults were `masterVolume: 0.85` (= −1.41 dB) and `masterSequencerVolume: 0.8` (= −1.94 dB); the other four were already `1.0` (= 0 dB). Those two fractional values are linear-scale artifacts nobody chose, and an unlabelled −1.9 dB drum trim is precisely the untracked calibration DEV-387 is about to do properly with a measurement. Existing sessions and existing `.solna` files are **converted**, not reset, so nobody's mix changes — only a brand-new project starts at unity. `SequencerTrack.volume` defaults to 0 dB for the D-383-1 reason below.

**4. D-383-1, as corrected: `SequencerTrack.volume` becomes a per-track `GainNode`, not a velocity multiplier — and migration resets it, never converts it.**
The field is stored, persisted and in the `.solna` body but read by nothing — Task 6 makes it audible for the first time, as a real gain node in the drum signal path. Its old values (0.7 … 0.9) were decorative. Converting them would apply −3.1 to −0.9 dB of attenuation that was never audible before, making every existing project quieter overnight. The migration therefore sets them to 0 dB and says so in its comment.

**5. Three version bumps per chain, not one — and they must NOT be collapsed during execution.**
Tasks 3, 5 and 6 each change a different set of keys and each ships a guard whose output is final at that commit. The three steps do genuinely different things — **convert** (`masterVolume`, linear→dB), **convert** (the five bus faders, linear→dB), **reset** (`sequencerTracks[].volume`, to unity, because its old values were never audible) — so they are not three instalments of one transform that could be written once. Reusing one version across three commits would leave sessions hydrated mid-series stamped as already-migrated with an incomplete shape and no later guard to revisit them — the failure mode `store.ts`'s existing `version < 15` comment already records. None of these steps is idempotent (a second run would read a dB value as linear), which is exactly why each gets its own guard.

**Do not merge 17, 18 and 19 into a single v17 while implementing**, however tempting it looks once you are holding all three transforms at once. Each task lands in its own commit, and each task's migration output is final at *that* commit — that is the whole property the separate numbers buy. One guard whose output grows across three commits is the same CLAUDE.md violation approached from the other side: sessions hydrated after commit one would be stamped with the final version while carrying only the first third of the transform, and nothing would ever revisit them. The same applies to the project chain's 8, 9 and 10. If a task is dropped or reordered, renumber the remaining ones so they stay contiguous and ascending — do not leave a gap and do not reuse a number.

**6. The sequencer fader is applied TWICE today; Task 4 fixes that before Task 5 converts it.**
Verified in three places: `engineSync.ts`'s `SOURCE_BUSES` sets `setSourceGain('sequencer', masterSequencerVolume)`; `engine.ts:727` connects `drumBusFilter` into that bus, so every drum voice passes through it; and `useSequencerPlayback.ts:150,161` *also* hands `masterSequencerVolume` to `triggerPad` → `triggerDrum(type, velocity)`, where `const v = clampVelocity(velocity)` scales every voice's peak (`peak: v * d.gain`). Drum output is therefore proportional to `masterSequencerVolume²` — at the 0.8 default that is 0.64 (−3.9 dB, not the −1.9 dB the value states), and at 0.5 the user gets −12 dB where the fader promises −6 dB. A squared fader law is exactly what an honest meter is supposed to expose, so it is fixed here rather than deferred. **Order matters:** converting a squared fader to dB first would only make the wrong curve easier to read precisely.
The fix is `useSequencerPlayback.ts` passing a real velocity (`DEFAULT_VELOCITY`, `0.8`) instead of a fader value; the bus gain already carries the fader. At factory defaults this is *inaudible* — `masterSequencerVolume` and `DEFAULT_VELOCITY` are both `0.8` today, so the product is unchanged — and it only diverges once the fader moves, which is the point.

**7. The per-track gain sits BEFORE the wet/dry split, and it is a node on the dry path with the wet seeded from it.**
`wireDrumVoice(env, reverbSend)` currently does `env.connect(drumBusFilter)` plus, when the kit authors a send, `env → send → drumSendFilter`. A track fader must move the reverb with the dry signal — pulling a track down while its tail stays up is not a fader, it is a filter — so the track gain goes *ahead* of that split. Concretely: the **dry** path routes through the persistent per-instrument `GainNode`, and the per-voice **send** gain is seeded as `reverbSend × trackGain.gain.value` at trigger time. The wet is not routed through the node itself for a specific reason: the track node is persistent and the send is per-voice, so `release()` — which disconnects the send's *outgoing* edges — would never sever the incoming edge from the persistent node, and every hit would leak one edge on it forever. Seeding the value is exact for a one-shot whose whole tail is shorter than the time it takes to move a fader.

**8. `Velocity` becomes a branded alias, and the rule is written where a reader hits it.**
`Decibels`/`Dbfs`/`LinearGain` already separate the three level kinds. The fourth conflation is the one that caused decision 6: a velocity is a per-hit performance attribute and a gain is a level a fader owns. `Velocity` joins them in `gainUnits.ts`, `triggerDrum`/`triggerSynthNoteOn`/`playbackNoteOn`/`triggerPad` name their parameter `velocity: Velocity`, and the rule sits in `gainUnits.ts`'s header and in `.claude/rules`-adjacent prose in `engine.ts` above `wireDrumVoice`.

**9. Recorded, deliberately NOT fixed in this issue.** Two more instances of the same conflation exist. Both are noted in code comments by Task 7 and belong to a follow-up:
- `DEFAULT_PADS` in `src/components/ui/DrumPadGrid.tsx` calls its per-pad strike strength `volume`. It is a velocity — it goes to `triggerDrum` as a performance attribute of one pad hit — and renaming it would touch the pad type, the persisted pad list and its tests, which is more than this issue should carry.
- `sequencerStepEvents`' `'note'` branch calls `playbackNoteOn(note, params, velocity, time)` and lets `source` default to `'synth'`, so a melodic sequencer track sums onto the **Lead** bus while the **Beat** fader is what the user reaches for. It is latent today only because all eleven canonical tracks are drum voices; the first synth/bass track a user adds makes it audible. Fixing it means deciding whether a sequencer note belongs on the sequencer bus at all, which is an arrangement question, not a units one.

**10. There is one fader component, because "unity at 0.75 of travel" cannot otherwise be enforced.**
After this plan lands, roughly twenty call sites must apply the same taper, the same `formatDb` readout and the same silence handling: the transport master fader, `ChannelStrip` (used by `ChordModulePanel`, `BassModulePanel`, `PadModulePanel`, `SynthView` and `SequencerView`), the five bus faders in `SortableLoopCard` and the eleven per-track drum faders from Task 6. Written at the call sites, the acceptance criterion "faders use the DAW-style taper, unity at 0.75 of travel" is not a property the code has — it is a claim about twenty copies, and the nineteenth is where it stops being true. `src/components/ui/VolumeFader.tsx` therefore owns the whole behaviour: the position↔dB conversion, `formatDb`, double-click-to-unity (the DAW convention, and only meaningful on a dB fader), the `-∞` detent (decision 11) and the accessible name. Every other component passes `valueDb` and `onChangeDb` and knows nothing about position.
It is not a channel strip. **DEV-389 owns the visual design and will pair this fader with a meter to make a real channel strip**; this task is about the behaviour living in one place, not about how it looks. `ChannelStrip` shrinks to icon + label + `VolumeFader` in the same move, which is what leaves DEV-389 one file to redesign.
The taper conversion stays *outside* `Slider`: `Slider` is a dumb `<input type="range">` used by dozens of non-level controls (cutoff, decay, swing), and teaching it about decibels would put a level unit into every knob-shaped thing in the app. `Slider` gains only two optional pass-throughs — `onDoubleClick` and `ariaLabel` — so that no second `<input type="range">` has to exist.

**11. Silence at the bottom of travel is TRUE silence — `-∞` displayed, `-60` stored, `0` at the engine.**
The contract already settles the *stored* half: silence is a finite `-60` because `JSON.stringify(-Infinity)` is `null` and these values cross `JSON.stringify` twice (divergence 2). This decision adds the display and audio halves.
*Display:* the fader's bottom detent shows `-∞ dB`, via `formatDb`, which is the only formatter. Every DAW's fader bottom reads `-∞`; a fader that bottoms out at "−60.0 dB" is telling the user there is more travel below it, and there is not.
*Audio:* `faderDbToGain` — the store→engine conversion, and the ONLY function `engineSync.ts` calls — maps exactly `SILENCE_DB` to linear `0`, not to `dbToGain(-60)`'s `0.001`. A muted-by-fader bus that still passes a thousandth of the signal is the same dishonesty as a fader that stops responding at +3.5 dB (decision 12), just quieter.
Three things make this safe rather than clever. The `-59.9 → -60` discontinuity is inaudible, because both values sit ~60 dB below anything the ear resolves in context, so it produces no click — a `setTargetAtTime` ramp from 0.001 to 0 is a ramp between two silences. `dbToGain` itself is NOT changed: it stays the pure conversion the contract pins, and `faderDbToGain` is the fader-shaped question built on top of it. And the sentinel is **named, never a bare `-60` literal** — `SILENCE_DB` in `gainUnits.ts`, re-exported as `FADER_MIN_DB` for the store's bounds — so the detent, the clamp, the two migration coercions and the engine boundary cannot be changed independently.
The detent itself is a *position* rule: the control's bottom detent returns exactly `SILENCE_DB` rather than whatever float the taper produces at `pos = 0`, because the engine boundary tests `db <= SILENCE_DB` and a `-59.99999999` would be silently not-silent.

**12. The engine clamps make the declared +12 dB unreachable, and the ceilings become derived.**
Neither the issue nor the first draft of this plan caught this, and it invalidates the fader range on its own:
- `src/audio/engine.ts:1422` — `setSourceGain` clamps with `Math.min(1.5, volume)`. `dbToGain(+12)` is `3.98`, so every bus fader silently stops at `1.5` — **+3.5 dB**. The top 8.5 dB of the throw does nothing.
- `src/audio/engine.ts:2446` — `setMasterVolume` clamps with `Math.min(1, vol)`. The master fader **cannot boost at all**; its entire top quarter of travel is dead.

```ts
import {
  FADER_MAX_DB,
  SILENCE_DB,
  UNITY_DB,
  dbToGain,
  gainToDb,
  toDecibels,
  toLinearGain,
} from '../utils/gainUnits';

/**
 * The store layer's dB vocabulary — the bounds, the default and the two
 * coercions that `sanitize.ts`, `store.ts`, `projectFile.ts` and BOTH
 * migration chains read. It exists so those six readers cannot drift: the
 * linear ranges they replaced were six hand-written literals (0..1 in three
 * places, 0..1.5 in eight), and two of them already disagreed about the drum
 * bus.
 *
 * Every value here is DECIBELS, relative, unity at 0 — never dBFS.
 */

/** Every fader starts at unity. See decision 3 in the DEV-386 plan. */
export const DEFAULT_FADER_DB: number = UNITY_DB;

/**
 * The bottom of the fader AND the stored representation of silence.
 *
 * murva's canonical `SILENCE_DB` is `-Infinity`, which survives its Zod
 * socket boundary. These values cross `JSON.stringify` twice — the persist
 * payload and the `.solna` body — and `JSON.stringify(-Infinity)` is `null`.
 * So silence is stored as a finite -60 dB: `dbToGain(-60)` is 0.001, which is
 * inaudible, and it coincides with `DISPLAY_FLOOR_DBFS`, so the fader bottom
 * and the silence value are the same place.
 */
export const FADER_MIN_DB: number = SILENCE_DB;

/**
 * The `<input type="range">` step, in POSITION (0..1), not in dB. A fixed dB
 * step is wrong on a tapered control — it is coarse at the bottom and absurd
 * at the top. 200 detents is ~0.4 dB below unity and ~0.24 dB above it.
 */
export const FADER_POSITION_STEP = 0.005;

/**
 * The five source-bus level keys, in the same order `SOURCE_BUSES` in
 * engineSync.ts declares them, so a reviewer comparing the two lists is
 * comparing sorted lists. `masterVolume` is deliberately absent: it is a
 * transport-slice key with no per-loop mirror, and it migrates on its own.
 */
export const BUS_FADER_KEYS = [
  'synthVolume',
  'chordVolume',
  'bassVolume',
  'padVolume',
  'masterSequencerVolume',
] as const;

export type BusFaderKey = (typeof BUS_FADER_KEYS)[number];

/** Coerce an unknown to a finite dB value inside the fader range. */
export function clampFaderDb(value: unknown, fallback: number = DEFAULT_FADER_DB): number {
  if (typeof value !== 'number' || !Number.isFinite(value)) return fallback;
  return Math.min(FADER_MAX_DB, Math.max(FADER_MIN_DB, value));
}

/**
 * Migration coercion: a pre-dB LINEAR gain becomes dB. Exact, so a mix set by
 * ear survives the unit change. A linear zero (or anything below it) becomes
 * FADER_MIN_DB rather than -Infinity, for the JSON reason above.
 */
export function linearToFaderDb(value: unknown, fallback: number = DEFAULT_FADER_DB): number {
  if (typeof value !== 'number' || !Number.isFinite(value)) return fallback;
  if (value <= 0) return FADER_MIN_DB;
  return clampFaderDb(gainToDb(toLinearGain(value)), fallback);
}

/**
 * THE STORE -> ENGINE CONVERSION. `engineSync.ts` calls this and nothing else;
 * it is not `dbToGain` with extra steps.
 *
 * At the bottom of the fader it returns EXACTLY 0, where `dbToGain(-60)` would
 * return 0.001. Every DAW's fader bottom is silence, not "very quiet", and a
 * bus a user has pulled all the way down must not still pass a thousandth of
 * its signal. The stored value stays the finite SILENCE_DB so it survives
 * JSON.stringify twice; this is the audio half of that same decision.
 *
 * The -59.9 -> -60 discontinuity is inaudible and clickless: both values are
 * ~60 dB below anything the ear resolves in context, and every consumer ramps
 * with setTargetAtTime, so the step is a ramp between two silences.
 *
 * A non-finite value is silence rather than NaN, because NaN written to an
 * AudioParam poisons the node for the rest of the session.
 */
export function faderDbToGain(db: number): number {
  if (!Number.isFinite(db) || db <= FADER_MIN_DB) return 0;
  return dbToGain(toDecibels(Math.min(FADER_MAX_DB, db)));
}

/**
 * Rewrites every `sequencerTracks[].volume` on one row to unity. Shared,
 * pure, and used by both migration chains — the only thing they share, in the
 * same way both lead chains share `upgradeLeadMelodyV1`. Non-mutating.
 */
export function resetTrackVolumesToUnity(
  row: Record<string, unknown>,
): Record<string, unknown> {
  if (!Array.isArray(row.sequencerTracks)) return row;
  return {
    ...row,
    sequencerTracks: row.sequencerTracks.map((track) =>
      track !== null && typeof track === 'object' && !Array.isArray(track)
        ? { ...(track as Record<string, unknown>), volume: DEFAULT_FADER_DB }
        : track,
    ),
  };
}
```

import React from "react";
import { Slider } from "./Slider";
import { FADER_POSITION_STEP } from "@/store/levelUnits";
import {
  SILENCE_DB,
  UNITY_DB,
  dbToSliderPos,
  formatDb,
  sliderPosTodB,
} from "@/utils/gainUnits";

/**
 * THE dB fader. Every user-facing level in the app renders through this
 * component: the transport master, the five ChannelStrip layers, the five bus
 * faders on a loop card and the eleven per-track drum faders — about twenty
 * call sites. That is the point. The taper, the readout, the unity reset and
 * the silence detent are behaviour, and behaviour written twenty times is not
 * a contract, it is twenty chances to disagree. A caller passes decibels and
 * gets decibels back; nothing outside this file converts a slider position.
 *
 * It is deliberately NOT a channel strip: no meter, no mute, no solo, no
 * name. DEV-389 pairs it with a meter to build one and owns the visual
 * design — this file owns only what the control DOES.
 */

/**
 * Position (0..1 of physical travel) -> decibels, with the bottom detent
 * pinned to the silence sentinel.
 *
 * The pin is not cosmetic. `faderDbToGain` maps `db <= SILENCE_DB` to a linear
 * 0, so silence has to arrive as EXACTLY SILENCE_DB; `sliderPosTodB(0)` is
 * float arithmetic over the taper and a -60.00000000001 would round-trip
 * through the store as a level that is very quiet instead of off. Half a step
 * is the width, so it catches the control's bottom detent and nothing above
 * it — the next detent up is a real, audible-in-principle -59.6 dB.
 */
export function faderPositionToDb(pos: number): number {
  return pos <= FADER_POSITION_STEP / 2 ? SILENCE_DB : sliderPosTodB(pos);
}

interface VolumeFaderProps {
  id: string;
  /**
   * The accessible name AND the tooltip prefix — "Chord Layer Gain" renders
   * as `aria-label="Chord Layer Gain"` and `title="Chord Layer Gain: -6.0 dB"`.
   * One prop, because a fader whose tooltip and screen-reader name disagree is
   * two controls to a reader who uses both.
   */
  label: string;
  /** DECIBELS, relative: unity is 0, the range is -60..+12. Never a position,
   *  never a linear gain. */
  valueDb: number;
  onChangeDb: (db: number) => void;
  /** Full daisyUI class list for the range, e.g. 'range range-xs range-accent w-16'. */
  className?: string;
  showReadout?: boolean;
  readoutClassName?: string;
}

export function VolumeFader({
  id,
  label,
  valueDb,
  onChangeDb,
  className = "range range-xs range-primary w-full",
  showReadout = true,
  readoutClassName = "text-[10px] font-mono w-14 text-right shrink-0 text-base-content/80",
}: VolumeFaderProps) {
  // formatDb is the ONE formatter for a dB value; the readout and the tooltip
  // are the same string, so they cannot round differently.
  const readout = formatDb(valueDb);
  return (
    <>
      {/* The control's value is a POSITION on the DAW taper (0..1, unity at
          0.75), and `step` is therefore a POSITION step: a fixed dB step on a
          tapered fader is coarse at the bottom and absurdly fine at the top.
          Rounding for humans is formatDb's job, not the control's. */}
      <Slider
        id={id}
        min={0}
        max={1}
        step={FADER_POSITION_STEP}
        value={dbToSliderPos(valueDb)}
        onChange={(pos) => onChangeDb(faderPositionToDb(pos))}
        // Double-click returns to unity. It is the DAW convention and it only
        // means anything on a dB fader, where 0 is a real home rather than an
        // arbitrary point on a 0..1.5 ramp.
        onDoubleClick={() => onChangeDb(UNITY_DB)}
        className={className}
        ariaLabel={label}
        title={`${label}: ${readout}`}
      />
      {showReadout && <span className={readoutClassName}>{readout}</span>}
    </>
  );
}

  const flat = { ...(state as Record<string, unknown>) };

    flat[key] = linearToFaderDb(flat[key], DEFAULT_FADER_DB);
  }

/**
 * The track gains reach the engine on a selector over `sequencerTracks`, not
 * one subscription per track: the roster is data, tracks can be added, and a
 * per-track subscription would have to be torn down and rebuilt whenever it
 * changed. The equality function compares only (instrument, volume) pairs and
 * short-circuits on reference identity, so an unrelated `set()` costs one
 * reference compare — which matters, because subscribeWithSelector runs every
 * selector on every set().
 */
function drumTrackGainsEqual(
  a: readonly SequencerTrack[],
  b: readonly SequencerTrack[],
): boolean {
  if (a === b) return true;
  if (a.length !== b.length) return false;

  return true;
}

    // to the bottom of its fader is silent rather than 60 dB down.

## Deferred — intentional future work, not oversights

**Variable velocity.** Velocity is a fixed constant on the sequencer step path (`DEFAULT_VELOCITY`, `0.8`) and this issue adds no velocity model: no per-step accents, no stored note velocity, no velocity lane, no velocity UI. That is a decision, not a gap — the sequencer had no velocity concept before, and inventing one while also changing the unit of seven level keys would make both changes unreviewable. The three velocity sources that *do* vary today keep working untouched: live MIDI (`midiInput.ts:150`), the bass patterns' authored accents (`bassPatterns.ts:130`) and the drum pads' per-pad strengths (`DEFAULT_PADS`).

**Adopting the `Velocity` brand at signatures.** `Velocity` and `toVelocity` are declared by DEV-384 (the shared contract lists them in its `gainUnits.ts` surface); this issue writes the rule beside them, but no existing signature is retyped.
