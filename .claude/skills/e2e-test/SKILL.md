# E2E Test Skill

## When to use this skill
- Writing new E2E tests (both single-user and multi-user)
- Fixing failing E2E tests
- Adding new API helpers in `e2e/helpers/api.ts`

## Run Commands

### Execution Order (mandatory)

1. Prepare backend + pass preflight at `http://localhost:3001` first.
2. Then run E2E commands in `app/frontend/`.

```bash
cd app/frontend   # Must always cd to frontend first

# Run all E2E tests (all browsers)
bun run test:e2e

# Interactive UI mode (view trace, screenshots)
bun run test:e2e:ui

# Headed mode (visible browser window)
bun run test:e2e:headed

# ── Per-group (chromium only) ──────────────────────────────────────
bun run test:e2e:auth       # e2e/auth/       — auth & lobby
bun run test:e2e:room       # e2e/room-lifecycle/ — room lifecycle & membership
bun run test:e2e:realtime   # e2e/realtime/   — real-time sync (excludes webrtc)
bun run test:e2e:project    # e2e/project/    — project rules & ownership
bun run test:e2e:webrtc     # e2e/webrtc/     — WebRTC voice & browser interop

# ── Serial one-worker group runs ───────────────────────────────────
bun run test:e2e:auth:w1
bun run test:e2e:room:w1
bun run test:e2e:realtime:w1
bun run test:e2e:project:w1
bun run test:e2e:webrtc        # runs WebRTC specs sequentially

# ── Optimized parallel/fast runs ───────────────────────────────────
bun run test:e2e:fast              # recommended E2E suite: auth parallel + room serial + realtime serial + project serial (excludes webrtc)
bun run test:e2e:parallel          # all chromium tests except webrtc, E2E_WORKERS=3, fullyParallel=true
bun run test:e2e:parallel:auth     # auth group, parallel
bun run test:e2e:parallel:room     # intentionally serial; alias for safe room-lifecycle run
bun run test:e2e:parallel:realtime # intentionally serial; alias for safe realtime run (excludes webrtc)
bun run test:e2e:parallel:project  # project group, parallel
bun run test:e2e:sequential        # all chromium groups serial (excludes webrtc)

# ── Repeat runs for flake checks ───────────────────────────────────
bun run test:e2e:auth:repeat
bun run test:e2e:room:repeat
bun run test:e2e:realtime:repeat
bun run test:e2e:project:repeat
bun run test:e2e:webrtc:repeat

# ── One-off commands ───────────────────────────────────────────────
# Run specific file
bun run test:e2e -- e2e/auth/auth.spec.ts --project=chromium

# List tests without running
bun run test:e2e -- --list
bun run test:e2e -- e2e/room-lifecycle/ --list

# Debug single test
bun run test:e2e -- e2e/auth/lobby.spec.ts --debug
```

> **Note:** `bun run test:e2e` runs `playwright test`, which requires the frontend dev server (`http://127.0.0.1:4173`).
> If the server isn't running, Playwright will start it automatically via `webServer` config (`bun run dev`).
>
> **Backend auto-start requirement for AI agents:**
> Before running E2E, the agent must start the backend automatically (if not already running) using one of these commands:
> - From project root (`collab-monorepo/`): `bun run dev:be`
> - From backend folder (`app/backend/`): `bun run start:dev`
>
> Backend must be ready at `http://localhost:3001` before starting tests.

### Backend Preflight Gate (required before running E2E)

Agents must pass this preflight before every E2E run:

1. Check if a process is listening on port `3001`.
```bash
lsof -nP -iTCP:3001 -sTCP:LISTEN
```

2. Perform a health check on the backend.
```bash
curl -fsS http://localhost:3001/api/health/simple | grep '"status":"ok"'
```

3. If health check fails or port has issues:
- Kill specifically the process holding port `3001`.
```bash
lsof -ti tcp:3001 | xargs kill -9
```
- Then restart the backend with the appropriate command for the cwd:
  - root: `bun run dev:be`
  - `app/backend/`: `bun run start:dev`
- Repeat health check until it passes.

4. Backend health check passing is necessary but **not** sufficient — continue to the fixture gate below.

### Fixture Preflight Gate (required before running E2E)

A healthy backend with an empty database fails in a way that looks nothing like missing data:
`global-setup` logs in, the login 401s, `waitForURL` sits for 30s, and every spec dies on a
timeout. Check the data *before* spending that 30s, so "not seeded yet" and "the app is broken"
stop looking identical.

5. Confirm the E2E users exist. **Guard on the database name first** — `.env` carries two URL
   sets with one commented out (see CLAUDE.md §11), so a misconfigured `DATABASE_URL` would
   otherwise let the next step write test users into staging.

```bash
DB=$(grep -m1 '^DATABASE_URL' app/backend/.env | cut -d= -f2- | tr -d '"')
case "$DB" in
  *collab_dev*) : ;;
  *) echo "REFUSING to seed: DATABASE_URL is not collab_dev — $DB"; exit 1 ;;
esac
psql "$DB" -tAc "select count(*) from users where email like '%@collab.local'"
```

6. Decide from the count — this is the branch that keeps the two failure modes distinct:

| Count | Meaning | Action |
|---|---|---|
| `0` | never seeded on this machine | seed (step 7) |
| `> 0` but auth still fails | **the test is genuinely broken** | do NOT re-seed — investigate; re-seeding hides the real failure |
| `> 0` and auth works | ready | run E2E |

7. Seed only when the count is `0`. `e2e:seed` is idempotent and takes ~1s, so re-running it
   is cheap — but always **bound it with a timeout** and **verify afterwards** rather than
   trusting its exit code alone:

```bash
bun run e2e:seed            # seeds users, then project/band fixtures
psql "$DB" -tAc "select count(*) from users where email like '%@collab.local'"   # must now be > 0
```

If seeding does not repair the count, stop and report. Do not start the E2E run — a suite that
begins without fixtures produces 30s timeouts that read as application bugs and will send
whoever reads the output chasing the wrong thing.

> **Why this gate is worth its length (2026-07-21).** `e2e:seed` had never once run to
> completion. `seed-e2e-users.ts` imported a backend singleton that held the event loop open,
> so it printed "Seeding completed." and hung forever; because `e2e:seed` chains the two
> scripts with `&&`, the project-fixture seed after it never ran at all. That hang masked three
> further bugs in the second script: `ensureProject` was called with its `(token, label, name)`
> arguments transposed (sending `Bearer user1`, which the API reported as `401 Invalid or
> expired token` — a message that points at credentials rather than at a caller that never sent
> one), the fixture set needed 5 projects against a `REGISTERED` cap of 3 (BR-5), and
> `GET /api/bands` omits `inviteToken` while the seed's type assertion claimed otherwise,
> producing `/api/bands/join/undefined` → `404 Invalid invite link`. None of it surfaced,
> because no spec consumes those fixtures — the suite passed 46/46 with the whole seed broken.
> Treat a green suite as evidence about the specs that ran, never about the fixtures they
> didn't touch.

For local pre-push confidence from the monorepo root, use:

```bash
bun run test:local:gate
```

This runs type-check, lint, unit tests, and `app/frontend`'s `test:e2e:fast`.

```env
E2E_USER_COUNT=12
E2E_USER1_EMAIL=...
E2E_USER1_PASSWORD=...
E2E_USER2_EMAIL=...
E2E_USER2_PASSWORD=...
E2E_USER3_EMAIL=...
E2E_USER3_PASSWORD=...
E2E_USER4_EMAIL=...
E2E_USER4_PASSWORD=...
# ...continue up to E2E_USER_COUNT
E2E_API_URL=http://localhost:3001   # optional, default = http://localhost:3001
```

`global-setup.ts` reads `.env` itself (no need to use `dotenv` in test files) and logs in every configured user.
`playwright.config.ts` caps workers to `floor(E2E_USER_COUNT / 3)` so a multi-user worker always has a distinct 3-account slice.

## E2E Placement, User Pool, and Parallelization Rules

Use this decision matrix before adding a new E2E test. Do not make a stateful multi-user test parallel just to make it faster.

| Feature/test type | Folder | Fixture/import | Users | Parallel policy |
|---|---|---|---|---|
| Login/logout, guest restrictions, session persistence | `e2e/auth/` | `@playwright/test` for guest/auth basics, or `../fixtures/e2e-test` when a logged-in per-worker user is needed | Guest or 1 authenticated user | Parallel OK |
| Lobby search, simple room create/navigation, hidden room visibility | `e2e/auth/` | Prefer `../fixtures/e2e-test` for authenticated tests | 1 authenticated user per worker | Parallel OK |
| Private room approval/reject, pending members | `e2e/room-lifecycle/` | `../fixtures/multi-user` | `page` owner + `user2Page` requester | Serial only |
| Room owner leave, ownership transfer, kick user | `e2e/room-lifecycle/` | `../fixtures/multi-user` | `page` owner + `user2Page`; add `user3Page` only if the rule needs a second successor | Serial only |
| Perform ↔ Arrange room switching / follow owner (BR-10) | `e2e/room-lifecycle/` | `../fixtures/multi-user` | `page` owner + `user2Page` follower | Serial only |
| Reconnect/reload/grace-period behavior (TR-6) | `e2e/room-lifecycle/` | `../fixtures/multi-user` if another user observes the state; otherwise `../fixtures/e2e-test` | Usually 1-2 users | Serial by default |
| Responsive runtime continuity and intentional leave (TR-15) | `e2e/room-lifecycle/` | Existing room lifecycle pattern | 1 authenticated user unless voice/role interaction requires more | Serial by default |
| Realtime sync that observes user A changing state and user B receiving it | `e2e/realtime/` | `../fixtures/multi-user` | `page` actor + `user2Page` observer | Parallel OK only across independent rooms/accounts; keep each describe serial |
| Project ownership/tools/BR-2/BR-12 shared-room behavior | `e2e/project/` | `../fixtures/multi-user` | `page` project owner + `user2Page` collaborator | Parallel OK across independent rooms/projects; keep stateful describe serial |
| Project limits, lock, visibility, save behavior for one user | `e2e/project/` | `../fixtures/e2e-test` or existing project helper pattern | 1 authenticated user | Parallel OK if data is isolated |
| UI-only checks with no backend persistence | Best matching folder | `@playwright/test` or `../fixtures/e2e-test` | Guest or 1 user | Parallel OK |

### Account Pool Rules

- Use `../fixtures/e2e-test` for logged-in single-user tests so each worker receives a different storage state from the pool.
- Use `../fixtures/multi-user` for any scenario requiring multiple simultaneous browser contexts. It assigns 3 users per worker:
  - `page` → offset 0
  - `user2Page` → offset 1
  - `user3Page` → offset 2
- Do not hard-code `e2e/.auth/user1.json` in new tests unless the scenario specifically requires a fixed account.
- Do not use the same logged-in account in two simultaneous browser contexts unless the test explicitly verifies same-account behavior.
- If a test needs more than 3 simultaneous registered users, extend the fixture first; do not open ad-hoc contexts with reused storage states.
- If `E2E_USER_COUNT=12`, at most 4 multi-user workers can run without account reuse. The config will cap requested workers automatically.

### Parallelization Rules

- `room-lifecycle` is intentionally serial in the fast path. These specs mutate room membership, ownership, approval state, reconnect/grace-period timers, socket namespaces, and Redis room state.
- Parallel is acceptable for groups where each test creates isolated rooms/projects and does not depend on global lobby order, shared project limits, grace-period timing, or long-lived audio/WebRTC room state.
- Keep realtime specs on a single worker in the fast path. Under `E2E_FULLY_PARALLEL=true`, the combined realtime group can saturate Redis/socket room state locks after prior suites and make join/member visibility assertions flaky.
- Use `test.describe.configure({ mode: 'serial' })` inside any file where tests share setup, depend on previous room state, or use multiple simultaneous users in the same room.
- When adding a new group script, prefer parallel only after proving the group passes with `E2E_FULLY_PARALLEL=true` and enough distinct users.
- If a parallel run fails but the same specs pass with `--workers=1`, investigate backend behavior and test isolation before weakening assertions.

### Test Data and Cleanup Rules

- Create rooms/projects with unique names using `uuidv4().slice(0, 8)`.
- Prefer API helpers for setup (`createRoomViaAPI`, project helpers) and UI for the behavior under test.
- Always leave rooms through fixture teardown or helper cleanup; do not rely on grace-period expiry.
- Treat HTTP 429, Redis lock timeout, dropped socket events, or unexpected lobby redirects as product/infrastructure signals, not just test flakes.
- Do not add arbitrary long sleeps to hide race conditions. Wait for visible UI state, URL changes, socket-observed member names, or API state instead.

## Cross-Browser E2E Testing Rules

While murva prioritizes cross-browser compatibility for audio and real-time events, running complex real-time, multi-user, or WebRTC voice tests in headless Firefox and WebKit is unstable in automated CI/CD environments due to driver, protocol, and hardware mock constraints.

Follow these guidelines when designing and writing E2E tests:

### 1. Engine Capabilities & Mock Limitations
* **Chromium (Blink)**: Best suited for full test suites, including WebRTC mock connections, Tone.js, and multi-user sync. Bypasses permissions and autoplay smoothly.
* **Firefox (Gecko)**: Supports basic mock captures and autoplay bypass. Skip advanced WebSocket routing intercepts (`page.routeWebSocket()`) on Firefox to avoid `NS_BINDING_ABORTED` page load abort errors.
* **WebKit (Safari)**: Does **NOT** support `'microphone'` or `'camera'` string permission injections in Playwright contexts (crashes with `Unknown permission` errors). Bypasses permissions implicitly for core flows but skip high-fidelity WebRTC/voice stream validation on WebKit, focusing instead on UI/UX, layouts, and forms.

### 2. Selective Cross-Browser Execution Policy
* Run single-user critical paths, user registration/login, lobby layout, forms, session persistence, and SEO checks (`e2e/auth/`, `smoke.spec.ts`) on **all 3 major engines (Chromium, Firefox, WebKit)**.
* For multi-user real-time sync, WebRTC voice meshes, metronome timing, and project lock tests, always enforce:
  ```ts
  test.skip(({ browserName }) => browserName !== 'chromium', 'Multi-user/WebRTC E2E runs on chromium only')
  ```
  to optimize test suite duration and prevent hardware isolation-related test flakes.

### 3. Local Binary Installation
If other browsers fail to launch locally with "Executable doesn't exist" errors, run:
```bash
bunx playwright install
```
This downloads all supported engine binaries into the local cache using the project's preferred package manager.

## Single-User Test (default pattern)

```ts
import { test, expect } from '@playwright/test'
import { v4 as uuidv4 } from 'uuid'
import { createRoomViaAPI } from './helpers/api'

// Default storageState = user1 (from playwright.config.ts)
// No need to declare test.use() if using user1

test.describe('My Feature', () => {
  test('description', async ({ page }) => {
    await page.goto('/')
    await page.waitForLoadState('load')

    const room = await createRoomViaAPI(page, {
      name: `E2E Test ${uuidv4().slice(0, 8)}`,
      roomType: 'perform',
    })

    await page.goto(`/perform/${room.id}`)
    await page.waitForLoadState('load')

    await expect(page.locator('button[title="Leave Room"]')).toBeVisible({ timeout: 15_000 })
  })
})
```

**Override user:** Add `test.use({ storageState: 'e2e/.auth/user2.json' })`
**Guest (unauthenticated):** Add `test.use({ storageState: { cookies: [], origins: [] } })`

## Multi-User Test (serial pattern)

```ts
import { v4 as uuidv4 } from 'uuid'
import { test, expect } from '../fixtures/multi-user'   // <-- multi-user fixture
import { createRoomViaAPI, leaveRoomViaAPI } from '../helpers/api'

// Multi-user tests must be serial and chromium only
test.describe.configure({ mode: 'serial' })
test.skip(({ browserName }) => browserName !== 'chromium', 'Multi-user tests run on chromium only')

test.describe('BR-X: My scenario', () => {
  let roomId: string

  test.beforeEach(async ({ page }) => {
    // user1 (page) setup
    await page.goto('/')
    await page.waitForLoadState('load')
    const room = await createRoomViaAPI(page, { name: `E2E ${uuidv4().slice(0, 8)}`, roomType: 'perform' })
    roomId = room.id
  })

  test('scenario description', async ({ page, user2Page }) => {
    // user1 joins
    await page.goto(`/perform/${roomId}`)
    await page.waitForLoadState('load')
    await expect(page.locator('button[title="Leave Room"]')).toBeVisible({ timeout: 15_000 })

    // user2 joins as band_member (session storage trick — direct nav = audience role)
    await user2Page.goto('/')
    await user2Page.waitForLoadState('load')
    await user2Page.evaluate((id) => {
      sessionStorage.setItem(
        'collab-room-session',
        JSON.stringify({ roomId: id, role: 'band_member', userId: 'e2e', username: 'e2e', timestamp: Date.now() }),
      )
    }, roomId)
    await user2Page.goto(`/perform/${roomId}`)
    await user2Page.waitForLoadState('load')
    await expect(user2Page.locator('button[title="Leave Room"]')).toBeVisible({ timeout: 15_000 })

    // Allow Socket.IO connections to establish
    await Promise.all([page.waitForTimeout(2_000), user2Page.waitForTimeout(2_000)])

    // Test assertions...
  })
})
```

**Available fixtures:** `page` (user1), `user2Page`, `user3Page`
**Every context has health check mock:** `/api/health` → `{"status":"ok"}`

## API Helpers (`e2e/helpers/api.ts`)

| Function | Description |
|---|---|
| `createRoomViaAPI(page, data)` | POST `/api/rooms` — create room without UI modal. Returns `LobbyRoom` |
| `listRooms(page)` | GET `/api/rooms` — returns lobby room list |
| `checkRoomExists(page, roomId)` | GET `/api/rooms/:id/exists` — returns `{ exists, userCount }` |
| `listUserProjects(page)` | GET `/api/projects` — returns `{ owned, contributed }` |
| `setProjectActiveRoom(page, projectId, roomId)` | PUT `/api/projects/:id/active-room` — binds project to room (`null` = clear) |
| `leaveRoomViaAPI(page, roomId)` | POST `/api/rooms/:id/leave` — leaves room via HTTP |
| `lockProjectViaAPI(page, projectId, isLocked)` | PATCH `/api/projects/:id/lock` — sets isLocked flag |

Every helper automatically reads auth token from `localStorage['auth_token']`.
`getUserIdentity` (private) reads `{ username, userId }` from `localStorage['user-store']` (Zustand persist).

**Add new helper:** Place in `e2e/helpers/api.ts` with JSDoc comment explaining the endpoint.
```ts
export async function myNewHelper(page: Page, ..., apiBase = DEFAULT_API_BASE): Promise<...> {
  const headers = await makeAuthHeaders(page)
  const res = await page.request.METHOD(`${apiBase}/api/...`, { headers, data: {...} })
  if (!res.ok()) throw new Error(`myNewHelper failed: ${res.status()} ${await res.text()}`)
  return res.json()
}
```

## Important Patterns

### 1. Wait for Socket.IO before asserting real-time state
```ts
await Promise.all([page.waitForTimeout(2_000), user2Page.waitForTimeout(2_000)])
```

### 2. Join room as band_member (not audience)
If navigating directly to `/perform/:id` without session storage → role = `audience` (can view UI but not interact).
Must set `collab-room-session` before navigating:
```ts
await user2Page.evaluate((id) => {
  sessionStorage.setItem('collab-room-session',
    JSON.stringify({ roomId: id, role: 'band_member', userId: 'e2e', username: 'e2e', timestamp: Date.now() }))
}, roomId)
await user2Page.goto(`/perform/${roomId}`)
```

### 3. Tests requiring specific data → graceful skip
```ts
const { owned } = await listUserProjects(page)
const arrangeProject = owned.find((p) => p.roomType === 'arrange')
if (!arrangeProject) {
  test.skip(true, 'No arrange project found for user1 — skipping BR-11 test')
  return
}
```

### 4. Mock API response (BR-5 pattern)
```ts
await page.route('**/api/projects*', async (route) => {
  if (route.request().method() === 'GET') {
    await route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify({ owned: [...], projectLimit: 2 }),
    })
  } else {
    await route.continue()
  }
})
// Must unroute after finished
await page.unrouteAll({ behavior: 'ignoreErrors' })
```

### 5. Guest flow
```ts
test.use({ storageState: { cookies: [], origins: [] } })
// ...
await page.goto('/login')
await page.getByRole('button', { name: /Continue as Guest/i }).click()
// Might have username modal before entering lobby
const usernameInput = page.getByPlaceholder(/username/i)
if (await usernameInput.isVisible({ timeout: 3_000 }).catch(() => false)) {
  await usernameInput.fill('GuestE2E')
  await page.getByRole('button', { name: /confirm|continue|ok/i }).click()
}
```

### 6. Avoid `page.waitForTimeout()` over 5 seconds
Use `expect(...).toBeVisible({ timeout: X })` instead of polling:
```ts
// ❌ Bad
await page.waitForTimeout(5000)
expect(await page.locator('.modal').isVisible()).toBe(true)

// ✅ Good
await expect(page.locator('.modal')).toBeVisible({ timeout: 10_000 })
```

## When E2E Test Fails — What to do?

**Rule:** E2E test fail ≠ wrong test necessarily.

### Decision flow

```
Test fail
   │
   ├─ Selector cannot find element?
   │     → Check selector first (read E2E_SELECTOR_POLICY.md)
   │
   ├─ Backend no response / 5xx?
   │     → Run preflight gate (see Execution Order above)
   │
   └─ Element exists, backend responds correctly, but behavior violates Rules?
         ↓
         Check if expected behavior aligns with RULES_AND_CONSTRAINTS.md
         │
         ├─ Rule says behavior "should" happen → means **bug in codebase**
         │     → Find bug in FE or BE and fix it
         │     → Do not fix test by lowering expectation
         │
         └─ Rule not specified / unclear → Ask user before deciding
```

### Summary
- **Tests are specs** — If test says behavior X should happen and RULES_AND_CONSTRAINTS.md confirms, codebase is wrong, not the test.
- Do not fix tests by reducing expectations without knowing the correct behavior.
- Bugs found during E2E → Create Linear issue immediately (see CLAUDE.md section 7).

## Common Mistakes

| Mistake | Fix |
|---|---|
| Import from `@playwright/test` in files under `multi-user/` | Import from `'../fixtures/multi-user'` instead |
| Forgot `test.describe.configure({ mode: 'serial' })` in multi-user | Must declare as the first line in file |
| Forgot chromium-only skip | `test.skip(({ browserName }) => browserName !== 'chromium', '...')` must be before describe |
| `getUserIdentity` throws error | Must `await page.goto('/')` before calling `createRoomViaAPI` / `leaveRoomViaAPI` for localStorage to load |
| Duplicate export in `api.ts` | Check before exporting new functions for name collisions |
| Real-time state doesn't update | Add `await page.waitForTimeout(2_000)` after socket connect |
